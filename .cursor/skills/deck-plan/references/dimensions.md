# 维度定义

十二个维度，分两级：`A`–`G` 全文级，一次确认，全程复用；`H`–`L` 页级，逐页确认。

## 切分理由

写在这里是为了让你能判断该不该改它，而不是照着填。

**全文级和页级的分界线是「会不会跨页复用」。** 风格、色板、排版、叙事骨架一旦
定了就要六页十页地重复用，属于全文级；页型、内容块这些每页都不同，属于页级。
分界线错了会导致两种病：全文级下放到页级，跨页就漂移；页级上提到全文级，
每页都被同一个模子框死。

**没有画布维度。** 下游只有 PowerPoint，默认 16:9。用户明确要 4:3 或其他比例时
记进锚点，不值得占一轮问答。

**没有图标维度。** 抓大放小，图标风格跟随视觉风格 `E`，由下游自行配。用户点名
要某个图标库时记进锚点的备注。

**叙事骨架不单列为维度。** 它是 `D` 大纲的推荐依据——先定骨架再据此生成逐页
主题，比单问一轮"你要金字塔还是叙事"更省事，用户看到的是大纲，不是术语。

**页级不含风格与色彩。** 它们在 `E`、`F` 已定，逐页重问是浪费。页级只处理
"这一页长什么样"，不处理"整本什么气质"。

**权重与关系拆成两维（`K` 与 `L`）。** 页型只隐含一种关系——`three_card` 隐含
三者并列、`comparison` 隐含两方对立——表达不了跨区域的关系。决议页用
`three_card` 能说清"三项复核并列"，说不清"批准建议与三项复核互为条件"，那是
跨越结论区与卡片区的关系。合并进 `K` 会让权重和关系两种信息混在一行，下游
解析时容易只取其一，所以单列。

## 1. 全文级维度

### `A` 受众与场景

**问什么**：谁看这份材料、在什么场合看、看完要能做出什么动作。

**为什么合并**：受众和场合几乎总是一起变（给董事会的现场汇报 vs 给同事的
异步阅读），拆成两问没有信息增益。

**推荐规则**：从用户的第一句需求里推断并复述确认，别空手问。用户说"给采购
部门过审"，就推荐「受众＝掌握预算的采购审批人；场合＝评审会现场，会后可能
被单独翻阅；期望动作＝当场批准或退回」。

**影响下游**：决定信息密度。现场有人讲解可以稀疏，独立阅读必须自足。把结论
记为锚点里的 `阅读模式`：`自足`（页面独立成立，信息完整）/ `讲解`（页面留白，
细节靠讲）/ `折中`。

### `B` 核心信息

**问什么**：整份材料如果只能留一句话，是哪句。

**推荐规则**：必须是一个可被反驳的主张，不是话题。「云服务器选型」是话题，
「建议批准以 g8i 8核32G 为主力的组合方案」才是主张。用户给的是话题时，
把它推进成主张再确认。

**影响下游**：每一页都要为这句话服务。逐页设计时若某页与它无关，先问用户
这页是否必要。

### `C` 材料源

**问什么**：数据、图片、引述从哪来。

**这是唯一必须实际验证的维度。** 逐条落实：

| 来源类型 | 验证动作 |
|---|---|
| 本地文件 | 用 Read 实际打开，确认可读且内容相关 |
| 网址 | 用 WebFetch 实际取一次，确认返回内容而非报错或登录墙 |
| 用户直接口述的数据 | 原样记录，标注「用户提供」 |
| 需要联网检索 | 先问用户是否授权检索；授权后检索，每条结果登记 URL 与检索日期 |

**验证失败就当场说，不要绕过。** 报告取不到的具体是哪一条、什么原因，请用户
换源、改为口述、或确认该项留空。

**登记格式**：每个来源给一个短标记（`M1`、`M2`……），记进锚点区的材料表，
后面所有引用都用这个标记。

**这是约束一的落地点**，也是整个 skill 里唯一不能靠下游推理补救的东西——
PowerPoint 能重排版面，但变不出它没见过的数据。

### `D` 页数与大纲

**问什么**：总共几页、每页讲什么。

**先定骨架再展开。** 从 [`narrative-modes.md`](./narrative-modes.md) 按选择规则
挑一个叙事骨架（或 `custom` 融合），再据此生成逐页主题。向用户展示的是大纲，
骨架名只作为一句理由带过。

**推荐规则**：页数由内容决定，不要迎合整数。用户给了上限就当硬上限。每页
必须能用一句话说出它的主题和核心，说不出的页合并或删掉。

**逐页摘要格式**（这一步只写四项，不涉及排版）：

```
P03 | 主题: 推荐套餐清单 | 核心: 四档按角色分工，年费合计 117,985.53 元
     | 材料: M1,M2 | 要点: 四档规格与单价 · 组合合计 · 不含项说明
```

**这是约束五的锚定点**。确认之后页数与顺序即冻结。

### `E` 视觉风格

**问什么**：整体看起来是什么气质。

**推荐规则**：按 [`visual-styles.md`](./visual-styles.md) 的选择规则匹配 `A` 的
场景和 `D` 的内容形态，不要按用户说的"高级感""大气"这类形容词直接映射——
先把形容词翻译成内容形态（"大气"通常是指留白多、单页焦点少），再匹配规则。

**风格不含颜色、不含字体。** 它只管形状语言、装饰密度、留白节奏、纹理层次。
颜色在 `F`，字体在 `G`。这条边界如果破了，风格库会退化成一堆改不动的硬编码。

### `F` 色彩方案

**问什么**：用哪套色，每个色承担什么语义。

**只选语义角色映射，不选"好看的配色"。** 从 [`palettes.md`](./palettes.md) 选
一组，或基于某组改。确认后锚点区记录的是角色到色值的映射表，每个角色带用途
说明和禁忌（例如「强调橙：只做填充与标记，对比度不足，绝不承载正文」）。

**推荐规则**：先看 `E` 的明暗底色需求（深色场风格不能配浅纸色板），再看 `A`
的场合正式度，最后看内容里有没有需要对立表达的两方（比价、竞品、正反）——
有的话就留意所选方案的强调色与次强调色区分度够不够，读者要能一眼分清哪个
数字属于哪一方。

### `G` 排版

**问什么**：中英文字体族、字号阶梯。

**推荐规则**：字体族按 `E` 的气质选，但**必须是下游环境大概率装有的字体**。
中文优先「微软雅黑 / 黑体 / 等线」，英文与数字优先「Arial / Calibri」。数字
密集的材料（财务、比价）单独给数据角色配等高数字字体，保证列对齐。

**字号阶梯给锚定值，不给区间。** 每个角色一个值，下游可在 ±2 的范围内微调
而不算新层级。角色至少覆盖：封面主标题 / 页标题 / 副标题 / 导语 / 正文 /
数据 / 注释 / 脚注。详见 [`typography.md`](./typography.md)。

## 2. 页级维度

### `H` 页型

**选什么**：从 [`page-types.md`](./page-types.md) 的 20 种 PowerPoint 版式里选一个。

**为什么用页型而不是描述布局**：下游是 PowerPoint，版式是它的原生概念。写
`kpi_dashboard` 一个词，它就知道大致骨架；写三百字的布局散文，它还得先理解
再翻译。**页型是这个 skill 里信息密度最高的一个字段。**

**推荐规则**：按内容形态匹配，不按页码位置。第一页不一定是 `title_slide`，
数据页不一定是 `chart_insight`。规则写在页型库里，照规则走。

### `I` 内容块

**写什么**：这一页有哪些信息块，每块承担什么角色、放什么内容要点。

**粒度**：块级，不是字级。写「结论句：四档单核年费一致，扩容无单价惩罚」，
不写完整措辞；写「对照表：四档 × 四项准则」，不写每个单元格。

**例外**：用户指定必须原样保留的措辞（法务声明、品牌口号、引述原文），
标 `[锁定]` 并写全文。

**每块指定排版角色**（标题 / 导语 / 正文 / 数据 / 注释 / 脚注），不写 px。

### `J` 材料引用

**写什么**：这一页用到哪些材料标记，以及每个事实性内容块的来源。

**格式**：块级标注，`来源: M1` 或 `来源: M2, M4`。

**没有来源的事实性内容不允许进入方案。** 缺就写 `[待补：<缺什么>]`，并在
交付时汇总告知用户。这条不能因为"用户大概知道"而放松。

### `K` 强调层级

**写什么**：这一页的视觉焦点是哪一块，次要是哪些，哪些是背景信息。

**为什么单列**：页型给了骨架，但骨架不知道哪块最重要。缺了这一维，下游会
把所有块画成等权，页面就"平"了。

**格式**：`焦点: <块名>` · `次级: <块名列表>` · `衬底: <块名列表>`。
一页只能有一个焦点。**如果说不出焦点，说明这一页的核心没想清楚**，回到 `D`
的该页核心重新推敲，而不是硬选一个。

### `L` 构图关系

**写什么**：这一页的内容块之间是什么逻辑关系。

**为什么和 `K` 分开**：`K` 管**权重**（哪块最重要），`L` 管**关系**（块和块
之间是什么逻辑）。两者正交。只给权重，下游知道谁大谁小，但不知道谁指向谁、
谁派生自谁——它会把所有块摆成互不相干的方盒子，页面各部分之间的推理链断掉。

**只用这六个词**：

| 关系 | 含义 | 典型内容 |
|---|---|---|
| `order` | 有先后顺序，顺序本身是信息 | 流程步骤、时间推进、先做 A 再做 B |
| `link` | 互相限定，一方是另一方的成立条件 | 结论与前提、建议与风险、数据与口径 |
| `parent` | 派生或从属，一方由另一方推出 | 合计与分项、差额与两个被减数、结论与证据 |
| `membership` | 同属一组，彼此平级 | 并列要点、同一批准则、一套方案的各档 |
| `contrast` | 对立，需要被并排比较 | 两家竞品、正反两面、前后对比 |
| `overlap` | 在某个维度上重合或一致 | 四档在单价上相同、两方在某项上打平 |

**禁止写形状。** 只写语义关系，不写「用大括号括起来」「加个箭头」「放在左边」。
形状是下游的事——同一个 `link` 关系，它可以用箭头、连接线、缩进层级或位置
邻近来表达，那是它按版式和留白条件做的判断，方案不该越俎代庖。

**格式**：一行，可以写多组关系，用分号隔开，括号里补一句为什么。

```
- 关系: 批准建议与三项复核为 link（每项复核都限定建议的成立条件）；
        三项复核之间为 membership；下一步与三项复核为 order
```

**关系是给下游的构图开关。** 全页只有 `membership` 时，用页型默认版式即可；
出现 `link`、`parent` 或 `order` 时，下游知道要额外做点什么来表达那个关系，
而不只是把块并排摆开。这就是这一维的全部作用——它不产生内容，只产生构图依据。

**只写页内关系。** 「这一页的口径决定了后两页的数字能否相减」是跨页关联，
不占这一行——它属于该内容块的 `[语义]` 约束补充。关系行混进跨页关联会让构图
开关永远处于打开状态，失去区分作用。

**说不出关系怎么办**：写 `关系: 无`。有些页面（纯封面、单一主张页）确实没有
块间关系，不要硬编一个。但如果一页有四五个块却说不出任何关系，通常是这一页
塞了不相干的东西，回到 `D` 看看该不该拆。

**开关不是每页都该开。** 数据密集的材料（比价、财报、方案对照）确实容易页页
出现 `parent`，那是内容性质决定的；但简报、目录、要点列表这类材料多数页面只有
`membership`，用页型默认排布就够。如果一份纯并列型材料里每页都写出了 `link`
或 `parent`，多半是在给关系硬找名目，回头检查一遍。
